# Native core measurements

September 7, 2026. Neo Archive now includes a Rust core for tweet text search, transactional archive writes, and xurl account selection. The CLI, ZIP/archive normalization, result hydration, web app, and transport adapter remain TypeScript. xurl owns OAuth credentials and consent.

## Correcting the import comparison

The [original XF comparison](2026-09-07-xf.md) measured a 100,000-tweet Neo Archive import at roughly 634 seconds. The number came from a real run, but it exposed two quadratic operations in the importer. Each tweet scanned the growing FTS table to replace its text, and revision-chain reconciliation repeatedly scanned the revision table.

The corrected SQLite importer scans existing FTS identifiers once and deletes by rowid. Its revision query keeps the reached component outside the indexed revision lookup. Repeated imports then took about 11 seconds before the native port. Comparing the old 634-second result with XF's 1.63 seconds did not measure a Rust-versus-TypeScript language difference. XF also imports less of Neo Archive's metadata.

The integrated Rust writer keeps the existing SQL rules and owns one transaction for the streamed import. Prepared statements stay cached in Rust. It preserves account ownership, tweet collections, messages, follow snapshots/events, revisions, supersession, and deletion records. Incomplete streams and count mismatches roll back.

## Import and memory

Both paths ran through the same packaged Neo Archive CLI and pinned Bun canary, using the same synthetic archive ZIPs and a fresh database for each run. Three runs per backend and size alternated execution order. The Mac was an M5 Pro with 24 GiB RAM. Rust was 1.98.0; Tantivy was 0.25.0. No private archive or live X account was used.

| Tweets | Corrected TypeScript median | Rust writer median | Time reduction | Median sampled peak RSS, TypeScript / Rust |
| --- | ---: | ---: | ---: | ---: |
| 10,000 | 1.519 s | 0.550 s | 63.8% | 213 / 178 MiB |
| 100,000 | 13.484 s | 3.579 s | 73.5% | 570 / 382 MiB |

The 100,000-tweet runs were 13.30, 13.48, and 13.88 seconds for TypeScript, and 3.44, 4.01, and 3.58 seconds for Rust. Memory sampling summed resident memory across the importer and its child processes every 20 ms; it includes the Rust process. This sampling can miss brief peaks and includes shared resident pages in more than one process. `/usr/bin/time -l` measurements are retained separately. The Rust child peaked around 37 MiB on this workload.

These import timings include ZIP parsing, normalization, database writes, and CLI output. They exclude the separate first construction of the Tantivy search index. Building that index from an existing 100,000-tweet SQLite archive took 0.83 seconds in a separate run, with a roughly 45 MiB process RSS peak. That is an index-build measurement, not a full archive import.

An early streaming invocation reported a broken pipe and was excluded. The adapter now prioritizes the native child's error over a secondary pipe error. Its receipts were retained; all twelve imports in the reported repeat completed successfully.

## Search and output parity

The integrated search comparison used the same 100,000-tweet corpus, ten queries, and eleven alternating passes. The first pass warmed caches and was excluded from timing statistics. Each remaining invocation started a fresh CLI process and returned the complete JSON response for the newest twenty matches.

| Backend | Pooled median | Pooled p95 |
| --- | ---: | ---: |
| SQLite | 178.61 ms | 293.64 ms |
| Rust/Tantivy | 153.42 ms | 190.04 ms |

Rust reduced median command time by 14.1% and p95 by 35.3%. All 110 paired responses were exactly equal, including hydrated fields. Common queries benefited more than misses and rare terms, where CLI startup dominates. The earlier proposed 20% median-and-p95 gate was not met on median search time; these numbers must not be described as meeting it. The native import reduction and improved search p95 support the requested Rust integration, with the measured search median stated separately.

These are warmed-index results. The index rebuilds after relevant database changes, so a search immediately after sync/import can take longer. Advanced tweet filters retain SQLite execution; DMs and links also retain their existing read models.

The tokenizer calls SQLite's `unicode61` tokenizer and supplies its tokens to Tantivy, preserving case, accents, and word boundaries. Results use chronological order with stable ID ties. Account scopes include the same-account intersection when both likes and bookmarks are required. SQLite remains authoritative: generation and database-instance checks detect changed data before result hydration. An existing caller transaction stays on SQLite so its uncommitted writes remain visible.

## Verification and receipts

The import comparison checked all 68 logical table instances across both corpus sizes. Row counts and sorted-row SHA-256 digests matched, excluding run-specific `observed_at` and `updated_at` fields and physical FTS shadow tables. Logical tweet and DM FTS tables were included. Mixed-data integration tests compare every logical table after import, reimport, and restore; only independently generated follow-event UUIDs are normalized.

The archive/database-writer suite passed 54 tests with native import enabled. The 69-test xurl suite passed through the real Rust routing process. Additional integration cases cover incomplete-stream rollback, native/SQLite output equality, account isolation, concurrent write detection, and caller transactions. Process-level authentication fixtures verify aliases and cancellation through an actual executable boundary. Those fixtures prove routing behavior without claiming live X access.

Raw measurements and source/build identities remain in the workspace's ignored `neotask-dev/local/neo-archive/rust-2026-09-07` directory. `native-imports-2` contains the accepted twelve import runs and table digests; `native-search` contains query samples and full-response comparisons. Earlier failed and intermediate experiments remain alongside them. The deterministic corpus generator is in the [benchmark script](https://github.com/NeotaskInc/neo-archive/blob/main/scripts/archive-search-benchmark.py).

To reproduce a backend comparison, build the same checkout once, use a fresh `NEO_ARCHIVE_HOME` and empty config for each import, then alternate `NEO_ARCHIVE_IMPORT_BACKEND=sqlite` and `rust` on the identical ZIP. Compare search with `NEO_ARCHIVE_SEARCH_BACKEND=sqlite` and `rust`, retaining full JSON responses and excluding only the declared warm-up pass. Keep active host load and memory measurements with the results.
