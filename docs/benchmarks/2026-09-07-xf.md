# XF and Neo Archive search comparison

Date: September 7, 2026. The command is `neoarchive`; `neo-archive` remains a compatibility alias. XF remains a separate installation.

## Decision

Keep the current search backend for this change. XF improved small-corpus command latency, rare-term searches, import time, and memory use. At 100,000 posts, it increased p95 search latency from 316 ms to 547 ms and returned different matches for some queries. It did not meet the acceptance gate set before measurement: at least 20% improvement in both median and p95 command latency, with compatible results and filters.

This rejects a direct XF substitution. A persistent Rust/Tantivy integration remains an unmeasured option. It would need compatible tokenization, efficient chronological retrieval, complete result hydration, and account/freshness guarantees before replacing the current path.

## Method

The baseline was Neo Archive commit `0e780b41d4edd70103b2c5003d7259e4d0b454da`, with the command spelling updated and its Birdclaw-derived search implementation unchanged. It ran on the pinned Bun 1.4.0 canary. The candidate was the installed XF 0.4.1 arm64 binary, built with Rust 1.99.0-nightly. Its SHA-256 was `d2e46106c1dfaefd39e684a190c57c0be5e70fde03729aa5e8b03858f50b1bad`. The [XF v0.4.1 release](https://github.com/Dicklesworthstone/xf/releases/tag/v0.4.1) resolves to commit `a824bd8083df48d237f939dd04553a69f404b000`.

Both tools imported the same deterministic synthetic tweet content at 10,000 and 100,000 posts. Both stored the full expected tweet count. This was one synthetic account, not Danny's personal archive or a live account test.

The production commands searched authored tweets and returned the newest 20 matches. XF used lexical mode, tweet filtering, descending date order, and no daemon. Embeddings were disabled during indexing. Neo Archive used its SQLite FTS5 read model; XF used its Tantivy search path.

Each corpus had ten queries spanning common terms, rare terms, multiple words, punctuation, accented text, Japanese text, and a miss. Eleven passes alternated engine order; the first pass was excluded. Measurements include process startup, query execution, hydration, and JSON output. File caches were warm. RSS came from macOS `/usr/bin/time -l` on an M5 Pro Mac with 24 GiB RAM.

Other work was active on the machine. Host telemetry was retained, and memory pressure increased near the end of the larger run. Treat the timings as observations of this controlled corpus, not universal product benchmarks. Mixed query families make the pooled median's confidence interval broad; per-query results are more useful for choosing an implementation.

This shows that startup contributes to command latency. A warm-engine comparison against Tantivy was not run, so these figures cannot establish which engine would win inside a persistent service.

## Import and storage

| Posts | Neo Archive import | XF import | Resulting storage, Neo / XF |
| --- | ---: | ---: | ---: |
| 10,000 | 6.884 s | 0.380 s | 17.2 / 5.2 MiB |
| 100,000 | 633.695 s | 1.633 s | 169.5 / 50.5 MiB |

These are whole import pipelines, including different metadata and storage work. Neo Archive consumes a ZIP and maintains richer account/read-model state. XF consumes the extracted directory. These numbers do not measure isolated index construction or prove a language-level speed ratio. Import was measured once at each size; the large Neo Archive run also received a one-second sampling profile.

The profile and query plan exposed repeated FTS table scans in [archive/apply.ts](../../src/lib/archive/apply.ts). Each tweet executes `delete from tweets_fts where tweet_id = ?` before reinsertion. SQLite reports a virtual-table scan for that equality predicate. This is a concrete import optimization target; no import algorithm change was included in this comparison.

## Result compatibility and output repair

Nine of the ten timed queries returned identical ordered tweet IDs at each size. The raw query `rust compiler` differed: Neo Archive requires both words, while XF's default query parser accepts either. Translating it to `rust AND compiler` resolved that probe. Accent handling also differs: `cafe` returned 45 and 449 Neo Archive matches at the two sizes, and zero XF matches. Exhaustive `rarequartz` searches returned the same 11 and 101 ordered IDs.

Matching tweet IDs does not establish full output parity. Neo Archive also returns account provenance, author records, collection state, and related tweet data. This benchmark did not establish XF parity for cross-account bookmarks, likes, DMs, restore/deletion behavior, or live index freshness. Relevance-ranked and semantic search were outside this comparison because they change the current ordering/matching contract.

The exhaustive checks found a separate Bun output bug: after the stdout stream had been initialized, `console.log` could emit only 65,536 bytes of a large piped JSON response and exit successfully. Neo Archive now writes JSON through `process.stdout.write`. A child-process regression test verifies complete Unicode JSON beyond the pipe buffer, and the production CLI returned all 449 accent matches and 101 rare-term matches after the repair. The timings above precede that output repair.

## Reproduction and next experiment

Run the [benchmark script](../../scripts/archive-search-benchmark.py) on macOS with both commands installed. Each output directory must be new:

```sh
python3 scripts/archive-search-benchmark.py --size 10000 --output /tmp/neoarchive-bench-small
python3 scripts/archive-search-benchmark.py --size 100000 --output /tmp/neoarchive-bench-large
```

The script saves the corpus, import records, raw search samples, checksums, confidence intervals, and ordered-ID comparisons. Original receipts are retained in the local `neotask-dev/local/neo-archive/benchmark-2026-09-07` task directory. The reusable harness uses the measured commands and corpus generator; subsequent runs use the installed revision, including any later fixes. Its final 10,000-post validation run completed after the output repair: Neo Archive median/p95 were 171.34/235.69 ms and XF 32.18/80.12 ms. Both tools ran slower than in the first session, illustrating the host-load limitation. This second run validates the harness and is not an isolated before/after measurement of the output repair.

Revisit a Rust backend after a candidate preserves the existing matching/account/output contract and avoids fetching every match to produce chronological results. Measure that candidate through the TypeScript caller, including synchronization and hydration costs. Re-run both latency gates, memory measurements, and complete-output checks before adopting it.
